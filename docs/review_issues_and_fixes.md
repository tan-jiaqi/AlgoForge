# 三个问题与处理

评审指出三个问题：KG 是否真正参与决策；提交的真实调用示例没有展示修复；相关机制主要靠 mock 验证。下面说明发现的原因、做的修改和现在的证据。

## 1. KG 是否真正参与决策

**发现的问题**
- 经验检索只按文本排序。演示 01（中文工单）进入提示词的 5 条经验全是客户流失场景的，"中文短文本字符级 TF-IDF"排第 6 被截掉。
- Planner 可以复用检索结果之外的算子；报告中的引用检查一栏固定显示"通过"。

**修改**
- `search_lessons` 先按诊断码和数据模态过滤，再按文本相关度与适用条件是否命中排序（`factory/kg.py`）。
- 复用的算子和参考的历史实现必须来自本轮检索结果；每步声明引用的证据 ID，范围检查的真实结果（含被拒绝的规划及原因）写入报告。
- 新增 KG 消融（完整 / 移除经验 / 仅算子目录）和搜索先验干预（固定子方案池，去掉 KG 历史）。

**证据**：演示 01 的检索结果包含字符级 TF-IDF 经验，方案采用 `char_wb`；消融中完整 KG 与仅算子目录选出不同方案；搜索干预中 4 轮有 3 轮入选集合改变。完整 KG 也会选不可解释的 LightGBM，所以结论是"KG 改变决策"，不是"KG 总让结果更好"。

## 2. 真实调用示例没有修复

**修改**
- 重新录制演示；网关对相同请求返回缓存回复，因此演示请求带试验编号，依次试了 3 个编号，保留第一个出现自然修复的（`factory/demo.py` 中的 `DEMO_TRIAL`）。
- 新增评测：自然失败探测、受控 NaN 注入 → 真实 LLM 修复 → 注册 → 新进程复用。

**证据**：演示 02 中 `ChargeRatioFeatureGenerator` 运行出错，修复 3 轮后通过，Curator 提炼出新经验；评测中有多次自然修复；注入链 3/3 走通。

## 3. 相关机制主要靠 mock

**修改与证据**：修复、经验提炼、Beam 搜索都有真实录制，回放只读取录制的 LLM 响应，其余（训练、验证、修复路由、知识回写）全部真实执行。搜索门槛设为 0.80 后，3 次真实搜索中 2 次从未达标的 LightGBM（0.624）找到正类加权的逻辑回归（0.848）。

## 过程中顺带修复的问题

| 问题 | 修复 |
| --- | --- |
| 参数一致性检查把 `None` 默认值、元组与列表的差异判为接口错误，LLM 反复"修复"不存在的问题 | `__init__` 默认值为 `None` 时不再判不一致 |
| `class_weight={0:1, 1:4}` 经 JSON 后键变成字符串，sklearn 报错 | 模型算子在 `fit` 时把字符串键对回真实类别 |
| 生成算子模块加载失败（如 MRO 冲突）时诊断不标算子，无法进入修复 | 沙箱记录每段源码所属算子，加载失败时标明 |
| 方案漏掉类别编码，字符串列直接进入模型 | 表格数据有类别列时，缺少 encoder 的方案在规划阶段被拒绝 |
| 生成算子未引用历史实现时不接入版本谱系 | 注册时以同名的上一版本作为 `DERIVED_FROM` 目标 |
| 搜索只扩展 1 轮、每轮只验证 1 个方案，先验又分不出参数差异 | 评测中设 beam 宽度 2、最多两轮；Beam 扩展提示词要求针对 `M_THRESHOLD` 直接调整决定该指标的参数 |
